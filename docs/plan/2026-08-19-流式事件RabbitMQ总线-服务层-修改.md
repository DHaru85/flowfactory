# 2026-08-19 流式事件 RabbitMQ 总线与缓存职责隔离 - 服务层 - 修改

## 用户需求理解

在应用层已有 SSE 协议状态机、但事件仍走 **uvicorn 进程内 `InMemorySseBus`** 的前提下，提出三组约束：

1. **Celery 工作流进程与 uvicorn 之间的流式事件中继改用 RabbitMQ**，不再用进程内 Queue，也不用 Redis Pub/Sub 作传输。
2. **高并发下隔离 Redis 与消息队列的职责**：缓存不做投递总线，队列不做热状态。
3. **在服务层更新基础设施**，使后续应用层 SSE 与 runtime 出流有稳定入口。

现状：Celery 已可用 `FLOWFACTORY_RABBITMQ_URL` 作**任务 broker**（队列 `wf.run` / `wf.beat` / `kb.ingest`）；Redis 承担 JWT、锁、配额、`conv:stream` 缓冲、`conv:sse:subscribers` 等。`ConversationCacheStore.add_sse_subscriber` 只登记连接 id，**从未作为事件通道**。Worker 的 `execute_envelope` 仍是 `ainvoke` 整段返回；LLM `complete()` 无 `stream=True`。token 增量是否纳入本期见澄清 Q2（**不是物理上做不到**，是当前路径没有增量、纳入会扩大 runtime 施工面）。

### 澄清过程

1. **Q1**：共用同一 RabbitMQ 集群可行；必须隔离不同类型队列。流式队列背压更保守，**优先保证任务提交通道可靠稳定**。
2. **Q2**：用户确认**扩大 runtime**，优先打字机效果；**流式帧不跑护栏**，护栏只作用于持久化内容（checkpoint / 落库 Message）。
3. **Q3**：应用层 SSE 消费改为 MQ subscribe；**在 uvicorn SSE 接口用 `asyncio.Queue` 承接**从 MQ 来的会话起止与 token 增量。

### 0. Q2：token 增量「本期做不到」指的是什么

这不是 RabbitMQ 或 SSE 状态机做不到，而是 **worker 今天根本不会产生 `speaking.delta`**。总线再快也只能转发已有事件。

当前叠了三层，缺一不可才会有 token 帧：

1. **LLM 客户端整段返回**（`service/runtime/llm.py`）  
   `chat.completions.create(...)` **没有** `stream=True`。`complete()` 的出参是完整 `str`。没有异步迭代器，应用层无法「转发不存在的增量」。

2. **生产路径 `ainvoke`，不是流式图 API**（`worker_loop.execute_envelope`）  
   `await graph.ainvoke(...)` 等整张图（或到 HITL）结束后才回到 Python。`FlowRuntime.astream_events` 已写但 **worker 未调用**。在此之前 API 最多知道「任务已入队」。

3. **llm 节点内部也是等完整回复再写 state**（`flow.py` `_make_llm_node`）  
   `content = await client.complete(messages)` 之后一次性追加 assistant 消息。观测/护栏包装的是**整节点**。出口 PII/敏感词若按 token 边生成边推，和「输出节点一次性过滤」的现有护栏模型冲突，要另定策略（例如先缓冲再推，或流式只推已过扫描的窗口）。

因此：**本期若只做 MQ 中继 + 生命周期事件，可以不改这三层。**  
**本期若要浏览器出现打字机效果，必须改 runtime/LLM（以及约定护栏与流式的关系），施工面从「总线」扩到「运行时出流」。** 不是 MQ 选型限制。

请用户确认：本期是否包含 token 出流（扩大 runtime），还是总线先通生命周期，token 下一期再接到同一 `ff.stream`。

**已确认纳入本期。** 护栏不作用于流式增量。

### 1. 职责隔离（硬约束）

| 设施 | 允许 | 禁止 |
| --- | --- | --- |
| **Redis** | 热状态、TTL、计数、分布式锁、JWT 黑名单、断线对齐缓冲（`conv:stream:{message_id}`）、订阅**在场**集合（`conv:sse:subscribers` 仅 connection id，非帧内容） | Pub/Sub / Stream / List 投递 SSE 帧；当任务队列用 |
| **RabbitMQ 任务 broker** | Celery 投递 `run_langgraph_flow` 等长任务 | 承载 token/SSE 帧 |
| **RabbitMQ 流式 exchange** | Worker → API 的 `SseEvent` JSON；多 uvicorn 扇出 | 存 JWT、锁、配额；持久化业务权威状态（权威仍在 Postgres） |

高并发含义：SSE 是高频小消息、多订阅者；Redis 适合 O(1) 读写热 key。用 Redis 当总线会与 JWT/锁争连接与内存，且 Pub/Sub 不持久、不易按 `conversation_id` 路由。RabbitMQ topic 按会话 routing key 投递，API 进程只收自己 bind 的会话。

### 2. 流式总线拓扑

```text
Celery worker                         RabbitMQ                              uvicorn 事件循环
独立 connection publish               ┌─ 任务队列 wf.* / kb.*  (Celery)     SSE handler
  帧可丢、超时丢弃 ──ff.stream──►     │  prefetch / ack 按任务可靠度        │
                                      └─ topic ff.stream                   ├─ AMQP consumer task
                                           routing conv.{id}               │    （独立 connection，
                                           进程独占 queue                    │     prefetch 保守）
                                           低 prefetch / 溢出丢帧            └─ put_nowait → asyncio.Queue
                                                                              → 状态机 → StreamingResponse
```

- Exchange：`topic`，名默认 `ff.stream`，durable；**与 Celery 队列名空间隔离**。
- Routing key：`conv.{conversation_id}`。
- **连接隔离**：流式总线使用**独立 AMQP connection（及 channel）**，不与 Celery broker 连接共用。流式拥塞不得堵住任务 `apply_async`。
- **流式背压（保守，保任务通道）**：
  - Consumer `basic_qos` prefetch 小（默认 1～8，可配 `stream_prefetch`）。
  - 帧 `delivery_mode=1`（非持久）；队列溢出或本地 `asyncio.Queue` 满：**丢帧并 ack/nack 丢弃**，不阻塞 broker、不反压到任务连接。
  - Worker 侧 publish：短超时，失败只打日志，**不重试打满**、不 raise 导致 Run 失败。
- 每个 uvicorn 进程：exclusive + auto-delete 队列，**有本地 SSE 才 bind**。
- Worker 只 publish `ff.stream`，不 consume。
- 无 `conversation_id` 的 Run 不发会话帧。
- Redis `conv:stream` 仍作断线对齐缓冲（热状态，不是队列）。

### 3. 服务层落点

新建 `src/backend/service/events/`（名称避免与 Celery「任务队列」混淆）：

```text
service/events/
  protocol.py    # StreamEventBus: publish / subscribe_conversation / unsubscribe
  schemas.py     # 复用或薄封装 SseEvent 字段（服务层不依赖 api.*）
  fake.py        # 内存实现，单测默认
  amqp.py        # aio-pika 生产实现
  factory.py     # get_stream_bus / set_stream_bus_override
```

- 服务层 **禁止 import `api`**。将 `SseEvent` 的传输 DTO 放到 `service/events/schemas.py`；应用层 `api/sse/protocol.py` 改为引用或保持字段兼容转换。
- 配置：`stream_amqp_url` 默认同 `rabbitmq_url`；`stream_exchange=ff.stream`；eager/无 URL 时工厂返回 Fake（与 `celery_eager` 开发态一致）。
- Celery `worker_process_init`：reset stream bus 连接（fork 后重建）。
- `execute_envelope`：有 `conversation_id` 时发布生命周期；llm 节点 `stream` 并 publish `speaking`（无护栏）。节点返回后既有 `wrap_guardrail_node` 对**完整输出**做 check_output，写入 checkpoint。
- Redis：`ConversationCacheStore` 标明 subscribers = 在场，不是总线；`conv:stream` 可追加已推文本供断线对齐。

### 4. 应用层 SSE（Q3 已确认）

```text
subscribe(conversation_id)
  → 服务层 StreamEventBus 对 MQ bind
  → 后台 consumer 协程把帧 put 进该连接的 asyncio.Queue
  → conversation_sse_iter 只 await Queue.get() + 状态机
  → StreamingResponse 写出
unsubscribe → unbind + 关闭 Queue
```

- **禁止**在 SSE 生成器里同步 `basic_get` 打满事件循环。
- `Queue` 有界（如 maxsize=256）；满则丢最旧或拒收并计数（与流式背压一致）。
- Fake 总线：不连 MQ，直接往同一 `asyncio.Queue` 投，单测保持现有写法。
- `api_reference_server.md`：中继为 `ff.stream`；接口侧为 Queue 协程消费。
