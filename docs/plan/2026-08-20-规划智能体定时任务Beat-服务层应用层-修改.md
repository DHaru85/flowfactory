## 需求中的待澄清事项

## 施工方案

### 1. 映射层 / Alembic

- `agent_beat_task.flow_id` 改为可空（仍 FK → `agent_flow`）。
- 新增可空 `profile_id` FK → `agent_profile`。
- Check：`(flow_id IS NULL) <> (profile_id IS NULL)`（恰一非空）。
- ORM `AgentBeatTask` 同步；`AgentProfile.beat_tasks` 关系。

### 2. 调度

- `dispatch_due_tasks`：有 `flow_id` 保持现逻辑（compile Flow / `kind=flow`）。
- 有 `profile_id`：`StartRunRequest(kind=planner, profile_id=..., flow_id=profile_id)`，**不**读 `agent_flow`、不传 `definition`。
- 规划输入：`input_payload` 若已是三槽则沿用；否则 `variables` + 可选 `messages`（`input`/`content` 作文案）。`metadata.app_key=planner`。
- 锁、croniter、`beat_system_user_id` 未配置则跳过：不变。
- `BeatTaskTriggerPayload`：`flow_id` / `profile_id` 均可空。

### 3. HTTP `agent_config`（共用 `/beat-tasks`）

- 创建：`flow_id` 与 `profile_id` **恰一**。仅 `flow_id` = 工作流（旧客户端）。仅 `profile_id` = 规划。皆空 `400 beat_target_required`；皆有 `400 beat_target_conflict`。Profile/Flow 不存在 `400`。
- 响应增加可空 `profile_id`；工作流任务该字段为 `null`（旧客户端多一个字段，可忽略）。
- PATCH 仍只改 `cron` / `input_payload`，不改绑定目标。
- 不调用 `PermissionService`。不做前端。

### 4. 文档与测试

- `data_schema_server.md`、`api_reference_server.md`、`service_layer.md`。
- 单测：规划触发不调 `flow.get`；工作流触发仍带 definition 路径；HTTP 恰一；旧「只 flow_id」回归。
- ruff；Alembic upgrade。
