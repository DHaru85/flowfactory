# 2026-08-20 规划会话发起失败排查 - 应用层服务层 - 修改

## 用户需求理解

检查 uvicorn 日志中 `POST /api/v1/conversations/planner/messages` 500，以及伴随的流式 publish 失败、SSE 非法转移。

检查结论：

1. **会话绑错了模型**：`conversation_id=27caf4fb-…` 的 `profile_id` 是 `prof-dce7152f`，默认 LLM `llm-dce7152f`（`model_name=demo`，`config={}`，现已 `is_active=false`）。同会话更早的 Run 已是 vLLM 404「model demo does not exist」；最近两次是 `Connection error.`，栈里 `UnsupportedProtocol: 'htttp://'`（三 t），不是 RabbitMQ 本身。
2. **eager 把图失败顶成 HTTP 500**：`celery_eager=true` 时 `apply()` 等整张图结束且 `task_eager_propagates=true`。LLM 一失败，`start()` 在路由里抛错，`run_submitted` 来不及由 API 发出。
3. **SSE 时序**：worker 已在图内发 `step_running` / `run_failed`，API 的 `run_submitted` 在 `start()` 之后。失败路径下连接已是 `failed`，再来一帧即为非法转移。
4. **流式 publish 失败**：Celery eager 在新线程 `asyncio.run` 新 loop 里跑图；`AmqpStreamEventBus` 却是进程单例，连接绑在 uvicorn loop 上。跨 loop publish 触发 0.2s 超时告警。Fake 总线仍应保持进程单例，否则单测/无 MQ 时 worker 写不进 API 的 Queue。

## 施工方案

1. **AMQP 按 running loop 实例化**；无 URL 时 Fake 仍进程单例。`reset_stream_bus` 清空 loop 表。
2. **`start_run` 在 `_send_celery` 之前** 对有 `conversation_id` 的 Run 发布 `run_submitted`；路由去掉事后重复 publish。
3. **workflow `apply_async` 在 eager 时 `throw=False`**：HTTP 返回 `run_id`，失败只走 SSE `run_failed` / 落库。
4. **发规划消息前校验默认 LLM 已启用**；`config.base_url` 若出现须为 `http://` 或 `https://`；客户端构造时同样校验并打日志。
